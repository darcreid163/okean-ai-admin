## 4. Этап 2 — закрыть #103 (P0, 1–2 недели)

Разбить #103 на три независимых issue/PR:

**2.1. Legacy и алиасы.**
Канонический fingerprint для одинакового запроса из REST, MCP и Cloud Batch;
нормализация алиасов; поведение для исторических строк без fingerprint
(их нельзя «угадывать» и удалять по возрасту). Тесты: разные entry points дают
один pending, а разные payload/actor — независимые операции.

**2.2. Операторская сверка и retention.**
Уже есть read-only диагностика (`/diagnostics/creation-intents`) — она ничего
не освобождает и это правильно. Нужен отдельный согласованный дизайн
reconciliation: сопоставление claim ↔ артефакт ↔ операция ↔ approval/Verify ↔
proof/receipt, затем явное действие, и только потом retention. Никакого TTL и
автоудаления. Тесты на синтетических фикстурах + реальный WP/MySQL.

**2.3. Транспорт и биллинг.**
Проверить повтор с тем же request key через REST/MCP/Cloud, неопределённый
исход, отсутствие повторного списания; Native 409 не должен трактоваться как
возврат в Cloud Ledger. Тест с реальным Gateway ledger на synthetic fixtures.

**Приёмка:** duplicate-создание не даёт лишних страниц/товаров/меню/workspace
файлов; неизвестные claim остаются удержанными; #103 закрывается или
превращается в явно принятый остаток с обоснованием.

## 6. Этап 4 — стенд как прод (P0, 1–2 недели)

Стенд должен совпадать с рабочими сайтами: PHP 8.3, MySQL 8, Beget-прокси/TLS/
кэш, GD **и** Imagick, реальные версии WordPress/Elementor/Woo/темы, права
каталогов, используемый DB drop-in, autocommit.

Матрица приёмки:
- content / Gutenberg / Elementor / Woo / media / menu / files:
  sandbox → approval → apply → Verify → receipt/proof → rollback → повторный
  Verify, без лишних артефактов;
- два владельца: изоляция сайтов и аккаунтов;
- OAuth: чистое согласие, выбранный/невыбранный сайт, отзыв, refresh после
  **реального** expiry (#92), только санитизированные логи;
- protected options, риск-политика, исторические операции — повторно;
- Skills/Abilities/Unsplash/CLI/Batch — по чеклисту, с выключенными
  неготовыми функциями.

Результат: протокол с датами, версиями, SHA и ссылками на доказательства.

## 14. Риски и запреты

- Репозиторий публичный: никаких реальных токенов, ключей, платёжных данных,
  клиентских данных и приватных бэкапов в коде, логах и переписке.
- Зелёный CI не равен приёмке и тем более продакшену.
- Не ослаблять Approval Engine, Verify, Receipt/Proof, Rollback, изоляцию
  OAuth и конфликт-гарды ради зелёного CI.
- Не выполнять миграцию тарифов, платежи, установку, теги и смену видимости
  репозитория без отдельного разрешения владельца.
- Гонки воспроизводятся нестабильно: фиксировать точный SHA и число прогонов,
  а не один удачный запуск.
