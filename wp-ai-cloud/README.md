# WP AI Cloud 0.1.0 — серверный пилот

Отдельный серверный WordPress-плагин. Он не меняет тему, страницы, WooCommerce, клиентский WP AI Admin или локальные разрешения на применение изменений. На коммерческом сайте пока не установлен.

## Реализовано

- Аккаунт привязан к WordPress user ID. Реестр сайтов с доказательством доступа через действующий MCP-токен администратора сайта.
- Единый gateway: `/wp-json/wpai-cloud/v1/mcp`, JSON-RPC, статeless JSON-режим Streamable HTTP для версий 2025-03-26, 2025-06-18 и 2025-11-25. GET/DELETE возвращают 405; уведомления возвращают пустой 202. SSE и сессий нет.
- Короткие gateway Bearer-токены (до часа), обязательные `site_id`, отдельные read/write scopes, разрешённый список сайтов в каждом токене, отзыв и проверка прав владельца на каждом HTTP-запросе.
- Центральная месячная квота аккаунта между всеми его сайтами. Атомарная резервация, уникальный ключ логического действия, зашифрованный кеш результата, успешный одиночный вызов = 1 действие, подтверждённая ошибка = 0.
- При потере ответа исход неизвестен: резерв сохраняется, повторное выполнение блокируется. Оператор сверяет локальную квитанцию, затем закрывает спорный запрос с сохранением зашифрованного доказательства. Никаких автоматических повторов изменяющих вызовов.
- HTTPS, запрет внутренних/специальных IP, проверка всех A/AAAA адресов и фиксация адреса cURL при запросе, проверка TLS, запрет редиректов и прокси. Исходящий URL берётся только из проверенного реестра.
- Vault XChaCha20-Poly1305 с привязкой шифротекста к аккаунту/сайту/запросу. Bearer-токены хранятся только как SHA-256. Приватные ключи не включены в пакет.
- Ограничение 120 MCP HTTP-запросов в минуту на аккаунт, 30 служебных запросов, 10 проверок подключения сайта. Журнал без аргументов и токенов.
- Ed25519 signer совместим с точным V1 verifier из клиентской ветки 2.1.10 (`d68a5dfa9f66abb57de7bc05e8ddb98f726c8a84`), неизменённая копия которого служит тестовым контрактом.

## Что эта сборка ещё не делает

Это начало сервера, не готовый платный SaaS. OAuth/PKCE/consent/refresh-token flow для самостоятельного подключения из ChatGPT, платежные webhooks, докупка пакетов, автоматические подписки, клиентский refresh/enforcement коммерческих entitlements, управляемый перенос владения сайтом и автоматический reconciliation ещё не реализованы. Не заявляется поддержка MCP 2026-07-28. Перед публичной бетой нужна реальная WordPress/MySQL/OAuth/MCP проверка на отдельной staging-установке.

Клиентский V1-контракт допускает только старые планы Free/Daily/Pro/Business и `quota.period=day`. Поэтому endpoint `/foundation` выдаёт **только доказательство совместимости**: Free/100/day и все 15 features. Он не выдаёт коммерческую месячную лицензию, не подключает и не меняет настройки локального плагина. Центральные Free/Pro/Power/Agency/Scale учитываются независимо. Локальная старая дневная квота клиента пока тоже действует. Для честного коммерческого запуска нужен V2-контракт и обновление клиента.

Batch-планирование/чтение доступно. Выполнение batch и массовые regression-запуски временно отклоняются одинаково на всех тарифах: доверенный учёт успешных объектов и правила остатка «1 действие за 5 объектов» ещё не утверждены. Одиночные инструменты доступны по одинаковому каталогу всех планов. Gateway публикует четыре служебных инструмента; полный каталог сайта возвращает `cloud_site_tools_list`, а отдельный вызов маршрутизирует `cloud_site_tool_call`.

## Развёртывание на Beget

Начать с отдельной staging-установки WordPress на текущем оплаченном хостинге. Не переносить маркетинговый сайт. VPS пока не требуется. Зарезервировать `api.wpaiadmin.ru`, `mcp.wpaiadmin.ru`, `staging.wpaiadmin.ru`; их DNS и TLS в этой работе не менялись.

Требуются PHP >=8.2, PDO MySQL, Sodium, cURL, MySQL/MariaDB InnoDB, HTTPS и возможность передавать Authorization header. Плагин создаёт только собственные таблицы с префиксом `<wp_prefix>wpai_cloud_`. Если расширений нет, установка/включение закрывается ошибкой, а не ослабляет безопасность.

1. Сделать резервную копию staging. Установить `wp-ai-cloud-0.1.0.zip` обычной установкой WordPress-плагина. При активации создаются 7 таблиц. Сервис выключен до конфигурации.
2. Администратор сервера запускает `php tools/generate-keys.php /absolute/private/wpai-cloud-keys.php` вне web root. Генератор создаёт новый файл 0600, не печатает ключи и не перезаписывает существующий файл. Добавить определения из него в `wp-config.php` до загрузки WordPress. Не хранить ключи в репозитории, uploads или базе. Если нужны нестандартные DB_HOST/IPv6/remote TLS, задать `WP_AI_CLOUD_DSN` и отдельно проверить настройки подключения к БД.
3. Проверить `/wp-json/wpai-cloud/v1/health`. Для обычного REST provisioning использовать WordPress Application Password по HTTPS или сессию с REST nonce. Сам gateway принимает только собственный Bearer-токен. Пароли не присылать в чат.
4. POST `/sites`: `{"home":"https://client.example.com","site_token":"<действующий MCP bearer администратора этого сайта>"}`. В ответе сохранить центральный `reg_...` — он отличается от UUID клиента.
5. POST `/tokens`: `{"site_ids":["reg_..."],"scopes":["mcp:read"]}`. Для разрешённых изменений явно добавить `mcp:write`. Токен показывается только в ответе создания, истекает через час. Это ручной pilot provisioning, не OAuth.
6. POST `/mcp` с `Authorization: Bearer ...`, `Content-Type: application/json`, `Accept: application/json, text/event-stream`, затем `initialize`, `notifications/initialized`, `tools/list`. При следующих запросах отправлять согласованный `MCP-Protocol-Version`.
7. Вызвать `cloud_sites_list` → `cloud_site_tools_list` с конкретным сайтом → `cloud_site_tool_call` с уникальным устойчивым `idempotency_key`. На клиенте сохраняется обычный локальный lifecycle sandbox/approval/apply/verify; gateway сам не одобряет изменения.

Пример тела одиночного чтения:

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"cloud_site_tool_call","arguments":{"site_id":"reg_<ID>","tool":"wp_get_site","arguments":{},"idempotency_key":"action-<UUID>"}}}
```

GET `/usage` и `/ledger` видит только свой аккаунт. DELETE `/sites/{id}` отключает связь и удаляет зашифрованный локальный MCP-токен. DELETE `/tokens/{sha256}` отзывает токен своего аккаунта. Оператор с `manage_options` может POST `/accounts/{WP_USER_ID}/plan` (`{"plan":"pro"}`); платежей это не подтверждает и остаток расходов не обнуляет.

Для неизвестного исхода нельзя повторять изменение с новым ключом. Оператор проверяет квитанцию и фактическое состояние на клиентском сайте, затем POST `/accounts/{owner}/requests/{request_key}/reconcile` с `outcome=succeeded|failed` и `evidence={note,receipt_sha256}`. Это ручная операторская аттестация, не автоматическая криптографическая проверка квитанции. Клиентам endpoint запрещён. Зависшие `dispatching` после падения процесса требуют отдельного расследования; их не снимает таймер.

## Проверки

```sh
php tests/run.php
```

Тесты используют настоящую SQLite/PDO транзакционную модель и 10 отдельных PHP-процессов; исходящий WordPress исполнен контролируемым fixture, а не реальным клиентским сайтом. Тот же набор запускается с `TEST_MYSQL_DSN`, `TEST_MYSQL_USER`, `TEST_MYSQL_PASSWORD` на отдельной пустой тестовой БД; **тест очищает все таблицы `cloud_test_*`**. Эти настройки запрещено направлять на production БД. CI отдельно проверяет MySQL и версии PHP.

Проверка реальных токенов WordPress, native REST nonce, OAuth-подключения ChatGPT, публичного DNS/TLS, реального sandbox/verify/rollback и восстановления после аварии процесса ещё требуется на staging. Перед обновлениями будущих версий нужна версия схемы и миграции; 0.1.0 устанавливается только впервые, не поверх старых экспериментальных Cloud-таблиц.

Квоты из `config/plans.json` предварительные: Free100, Pro500, Power2000, Agency5000, Scale10000 за календарный месяц UTC. Политику может заменить администратор через `WP_AI_CLOUD_POLICY_FILE` без обновления клиентского плагина. Изменения проходят отдельное ревью и получают новую версию; уже созданные запросы сохраняют свою версию политики. Новые продажи не включать до закрытой беты на 5–10 аккаунтах.
