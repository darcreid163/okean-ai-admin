# WP AI Admin Cloud Core 0.2.0 — operator gateway pilot

This is an in-place update of the recovered `wp-ai-admin-cloud-0.1.0.zip`, not the separate `wp-ai-cloud-0.1.0.zip` prototype. Keep WP AI Admin 2.1.9 active. Use wpaiadmin.ru itself as the authorized test site. The existing website design is unaffected.

## Install and test on wpaiadmin.ru

1. WordPress → Plugins → Add new → Upload `wp-ai-admin-cloud-0.2.0.zip` → replace the installed **WP AI Admin Cloud Core**. Its folder and main file are unchanged: `wp-ai-admin-cloud/wp-ai-admin-cloud.php`.
2. Open **WP AI Admin Cloud** in the administration menu. Click **Включить тестовый gateway**. PHP 8.2+, PDO MySQL, Sodium, cURL and HTTPS are required. Detailed failure codes appear in the panel.
3. Paste an administrator MCP token generated by the local WP AI Admin plugin into **Подключить этот сайт**. This token remains encrypted on the server. Do not send it in chat.
4. Click **Получить токен gateway на 1 час**. Copy the token displayed once. Its hash can be used to revoke it. Obtain another token after expiry.
5. Paste that gateway token into **Проверить gateway через HTTPS**. The test checks actual HTTPS REST initialize, empty notification response, gateway catalog, scoped site list, full native catalog and monthly usage. Six checks, zero billable actions, no content writes.
6. For an independent client use `https://wpaiadmin.ru/wp-json/wpai-cloud/v1/mcp`, Streamable HTTP, and header `Authorization: Bearer <gateway token>`. The token is an Inspector/test credential, not ChatGPT OAuth onboarding. Origin is same-site by default; an Inspector origin must be explicitly included in `WP_AI_CLOUD_ORIGINS` if its browser sends Origin. Preserve the exact origin shown by the client.

No SSH or manual key copy is required for the panel workflow. Keys are generated once, wrapped using a key derived from the installation's AUTH_KEY and AUTH_SALT, and stored in a non-autoloaded option. Back up wp-config.php and the database together. Changing these WordPress keys without migrating gateway keys prevents decrypting credentials and receipts. Server-side keys can instead be supplied with WP_AI_CLOUD_VAULT_KEY / WP_AI_CLOUD_SIGNING_KEY. WP_AI_CLOUD_ENABLED, if defined, overrides the panel toggle. A separately installed `WP AI Cloud` prototype must be deactivated to prevent competing routes.

## Compatibility and storage

The Core v1 installer, plan seeding and public status/plans contracts are preserved. `wpai_cloud_db_version` remains 1. All 11 existing `${wpdb->prefix}wpai_*` tables are unchanged; no DROP, ALTER, reset or import is performed by the gateway migration. A separate `${wpdb->prefix}wpai_gateway_*` schema holds pilot connections, encrypted credentials, token hashes, execution ledger, reservations and rate limits. `wpai_gateway_db_version=1` is recorded only after its migration succeeds. Repeated enables preserve data and keys.

The Core account row is reused by WordPress user ID; suspended Core accounts are denied. Plan limits and billing flags come from active Core plan versions, not a second production catalog. Gateway usage is a separate **pilot execution ledger**. It does not activate existing commercial licenses, import existing license balances, or replace the legacy usage tables. Operator plan overrides are test-only and not paid licenses.

The original provisional monthly limits remain Free 100, Pro 500, Power 2000, Agency 5000, Scale 10000. All plans expose the same native catalog. Unknown or incompatible plan versions fail closed.

## Gateway security and accounting

Provisioning and gateway usage are limited to WordPress administrators in this release. Administrator forms require nonce and HTTPS. REST provisioning requires WordPress authentication plus manage_options. Gateway Bearer tokens never authorize provisioning. Short-lived gateway tokens are hashed, tenant/site bound, scoped, revocable, and rechecked on every call. Site credentials and cached responses are encrypted with authenticated per-account binding. HTTPS upstream calls reject private/reserved addresses, pin public DNS results, verify TLS and refuse redirects/proxies.

Four gateway tools: cloud_sites_list, cloud_usage, cloud_site_tools_list, cloud_site_tool_call. Always supply an explicit registered site_id. A stable idempotency key identifies one logical request; a retry returns the original receipt and never redispatches it. Reusing the key with different site/tool/arguments fails.

Successful single native tool calls currently cost one pilot action. Failures cost zero. Verification, operation receipts/proofs/status/diff and operation/batch rollback cost zero and remain available at exhausted monthly quota. Write-scoped credentials and native approvals remain necessary for rollback. Free calls still have an idempotent ledger entry. Quotas use calendar months in UTC and one account balance across connected sites. Concurrent reservations are atomic in InnoDB. Unknown outcomes hold reservations, prevent redispatch and require operator reconciliation using independently checked receipt evidence. Free uncertain outcomes reserve zero and remain free when reconciled.

## Remaining work before commercial release

- OAuth 2.1 / PKCE, consent, discovery, refresh/revocation and ChatGPT connection.
- Commercial client entitlement V2; the V1 foundation endpoint is compatibility proof only. The local client's old daily quota can still block work.
- Receipt-based logical intent accounting: avoid billing sandbox and apply twice; batch must use ceil(successful_objects/5) across all chunks/retries. Batch mutations and regression batches remain blocked pending that contract; rollback remains available.
- Central license enforcement and recovery after license expiry; the pilot does not enforce commercial license state.
- Crash recovery for requests stuck in dispatching, automated verified receipt reconciliation, retention and monitoring.
- Cabinet, payments, renewal/top-ups, beta tests and public plugin review.

This build is not installed automatically. The actual wpaiadmin.ru HTTPS/auth/runtime test must be run after installing and enabling it. The panel reports its own test result; local/CI tests do not imply the live test passed.
